# Design: Habitat rover path classification (pick the correct candidate)

**Date:** 2026-07-20
**Status:** approved design, implemented
**Companion to:** `2026-07-17-habitat-path-visibility-design.md` (path regression)

## Context

The Habitat path-regression phase produced strong results (LoRA reaches 0.066 median
waypoint error and 0.83 per-waypoint visibility accuracy vs. an unusable base model).
Before adding reasoning traces, we test a **second task on the same dataset and the same
frames**: each sample offers several candidate paths, and the model must pick the
traversable one.

This is discrimination rather than generation. It probes whether the model actually
understands traversability instead of regressing a plausible-looking curve, and it maps
onto how a deployed rover would choose among planner proposals.

## Goal

Fine-tune Qwen3.5-2B (LoRA) to take an `fpv_enhanced.png` frame with candidate paths
drawn on it and answer `{"choice": N}`, then evaluate base vs. LoRA across training-set
sizes — mirroring the regression scaling study, with classification metrics.

### Non-goals
- Reasoning/`<think>` traces (still deferred; `meta["rationale"]` is the natural future
  target — it is a natural-language justification referencing candidates by index).
- Any change to the regression task, its splits, or its results.
- Joint multi-task training (classification + regression in one adapter).
- Asking the model to output the *set* of acceptable paths — single best choice only.

## Source data (verified over all 4,398 samples)

Same dataset root and sample layout as the regression phase. Additional fields used here:

- `fpv_paths.json` → `candidates[i]` with `runs`, `badge_uv`, `frac_in_fov`, `frac_hidden`.
- `meta.json` → `label` (canonical correct index), `accepted` (all acceptable indices),
  `margin`, `near_symmetric`, and `candidates[i]` with `display_index`, `label`
  ("left"/"right"/"direct"), `feasible`, `score`.

Facts established by a full-dataset audit (`4398/4398` unless noted):

| Property | Result |
|---|---|
| `candidates[i]["display_index"] == i` | 4398/4398 — the badge number *is* the dataset index |
| `label ∈ accepted` | 4398/4398 |
| `accepted == {i : candidates[i].feasible}` | 4398/4398 |
| candidate count | `{3: 2335, 5: 2043, 4: 12, 2: 8}` |
| `len(accepted)` | `{1: 2369, 2: 2020, 3: 9}` — **46% have >1 acceptable answer** |
| kind of the correct candidate | `{left: 2204, right: 2183, direct: 11}` |
| `correct_path_in_fov` | 4160 |

**The `direct` shortcut.** Every sample contains a straight-line `direct` candidate, and
it is the correct answer in only **11/4398 samples (0.25%)**. A model that learns nothing
but "never pick the straight line" lifts accepted-accuracy from ~0.36 to ~0.49. This is
the single biggest threat to interpreting the results, so the shortcut is *measured*
rather than removed: `prepare_habitat_choice.py` writes both chance baselines into
`meta.json`, the eval reports `picked_direct_rate`, and the scaling plot draws the
"chance, no direct" line as the bar that actually has to be beaten.

## Rendering

The source `fpv_enhanced.png` is a clean, unannotated render — the composite image is
generated by us into gitignored `data/`; the source dataset is never written to.

- Coordinates normalize by `fpv_paths["image_size"]` (512), **not** by pixel size (1024).
- Each candidate's runs are flattened and clipped to the unit square with the regression
  phase's `clip_polyline_unit` (reused, not reimplemented) — raw coordinates reach
  ~2500 px and would otherwise draw far outside the frame.
- Each candidate is drawn in a distinct Okabe-Ito colorblind-safe color with a white
  underlay for contrast, plus a **numbered badge** so color is never the only channel.
- Output: 768×768 JPEG q90.

**Badge placement.** The dataset's own `badge_uv` is unusable as-is: measured over 800
samples, **32% of badges fall outside the frame** (affecting 58% of samples) and 566
badge pairs overlap. Left uncorrected, candidates would be unlabeled or ambiguous and the
task would be unanswerable. `badge_positions()` therefore uses `badge_uv` only when it is
in-frame and clear of already-placed badges, and otherwise walks the candidate's own
clipped polyline for a free spot. All candidates of every in-FOV sample are drawable
(566/566 sampled), so no samples are lost to rendering.

## Task format

**Prompt** (fixed, no per-sample text):
> `<image>`
> You are a rover navigating an indoor environment. Several candidate paths to the goal
> have been drawn on the image, each marked with a numbered badge. Exactly one of them
> should be chosen: the path that is actually traversable and does not run through walls,
> furniture or other obstacles. Reply with the number of that path as JSON:
> `{"choice": N}`.

**Answer:** `{"choice": N}` where N is the dataset's candidate index (= the badge number).

**Record:** the standard 1-image / 2-turn shape plus a `choice_meta` sidecar
(`label`, `accepted`, `n_candidates`, `kinds`, `margin`, `near_symmetric`). The sidecar
carries what the answer string cannot — the accepted set needed for scoring.
`TrajectoryDataset` reads only `id`/`image`/`conversations`, so **training needs no code
change at all**.

## Splits

Split membership is **copied from `data/prepared_habitat/`** rather than re-shuffled, so
classification and regression run on exactly the same frames and can be compared sample
by sample ("traced the path well but chose the wrong candidate"). Eval-vs-train
disjointness is re-asserted anyway.

## Metrics

Accuracies are computed over **all** eval samples — an unparseable answer counts as
wrong, so the headline number is never inflated by dropping failures (`parse_rate`
reports those separately). This differs deliberately from the regression task, where
position error is only meaningful over parseable outputs.

- `parse_rate`, `valid_choice_rate` (index within `[0, n_candidates)`)
- `strict_accuracy` — against the canonical `label`
- `accepted_accuracy` — against `accepted`; **the headline metric**, since 46% of samples
  have more than one valid answer and strict accuracy would unfairly punish them
- `chance_strict` / `chance_accepted`, and the same **excluding `direct`**
- `picked_direct_rate` — how often the model falls into the trap it should have learned
- breakdowns by `n_candidates` (3 vs 5) and by `near_symmetric` (the genuinely hard ones)

## Risks / open questions

- **The `direct` shortcut** dominates interpretation; always read accuracy against
  `chance_accepted_excluding_direct` (~0.49), not against raw chance (~0.36).
- **Base-model prior on small integers:** a zero-shot model may emit "1" reflexively.
  `valid_choice_rate` and the per-`n_candidates` breakdown expose that.
- **Color/index binding:** candidate *i* always gets palette color *i*. Since `label` is
  near-uniform over indices, this leaks nothing, but it does mean the model may key on
  color rather than badge; worth probing later by shuffling the palette at eval time.
- **Near-symmetric samples** (`near_symmetric`, low `margin`) may be close to
  undecidable from a single frame; reported separately rather than dropped.
