# Design: re-run both Habitat experiments on Qwen3.5-0.8B

Date: 2026-07-20

## Goal

Answer one question: **what performance is reachable on the two Habitat tasks with a
2.5×-smaller base model?** Both experiments — path regression (`--task habitat`) and
path classification (`--task choice`) — are re-run on `Qwen/Qwen3.5-0.8B` with every
other variable held fixed, and the resulting scaling curves are overlaid on the
existing 2B curves.

Explicitly a controlled A/B on model size, not a tuning exercise. LoRA rank/alpha/
dropout, learning rate, effective batch size, epoch count, data splits and seed all
stay exactly as they were for the 2B runs. If 0.8B underperforms, that result is
attributable to capacity at this fixed budget; a follow-up LR check is out of scope
here and would be its own experiment.

## Constraints

- **Existing 2B results are frozen.** No stage of this work writes to `outputs/eval`,
  `outputs/eval_habitat`, `outputs/eval_habitat_choice`, or `outputs/runs`.
- Only the 0.8B sweeps are launched. The 2B sweeps are not re-run.
- No new data prep: `data/prepared_habitat/` and `data/prepared_habitat_choice/` are
  model-independent and reused as-is, so both models see identical frames and splits.

## Preflight result (already verified, 2026-07-20)

`Qwen/Qwen3.5-0.8B` is present in the NFS HF cache (1.7 GB, complete snapshot) and is
architecturally the same shape as the 2B: `Qwen3_5ForConditionalGeneration`, 24 decoder
layers, `linear_attention`×3 + `full_attention` interval-4. A meta-device module dump
confirms `LORA_TARGETS_TEXT` matches with the same per-layer counts the 2B list was
written for:

| target | matches | note |
|---|---|---|
| `q_proj` / `k_proj` / `v_proj` / `o_proj` | 6 each | full-attention layers |
| `in_proj_qkv` / `out_proj` | 18 each | linear-attention layers |
| `gate_proj` / `up_proj` / `down_proj` | 24 each | all MLPs |
| `qkv` / `proj` / `linear_fc1` / `linear_fc2` | 12/12/13/13 | vision tower, all vision-side |

**No change to `LORA_TARGETS_TEXT` or `LORA_TARGETS_VISION` is required.**

## Components

### 1. Model plumbing

`--model-id` on `scripts/train.py` and `scripts/evaluate.py`, defaulting to
`Qwen/Qwen3.5-2B`. The default preserves the behaviour of every existing command and
sbatch invocation exactly.

The resolved model id is recorded in the outputs so a result tree is self-describing
instead of depending on recall:

- `evaluate.py` → `model_id` key in `metrics.json`
- `train.py` → `model_id` in the run dir's saved training config

### 2. Output namespacing

`slurm/run_all_habitat.sbatch` and `slurm/run_all_habitat_choice.sbatch` accept an
optional model argument:

```
sbatch slurm/run_all_habitat.sbatch 0.8b
sbatch slurm/run_all_habitat_choice.sbatch 0.8b
```

| arg | model id | path suffix |
|---|---|---|
| *(none)* / `2b` | `Qwen/Qwen3.5-2B` | `""` — identical to today |
| `0.8b` | `Qwen/Qwen3.5-0.8B` | `_0.8b` |

An unrecognised argument is a hard error, not a silent fallback to 2B — a typo must
never quietly write into the frozen 2B trees.

The suffix goes on the **tree**, not on names inside it:

```
outputs/runs_0.8b/habitat_train_500/
outputs/eval_habitat_0.8b/habitat_train_500/metrics.json
outputs/eval_habitat_choice_0.8b/habitat_choice_train_500/metrics.json
```

Eval **tags stay unchanged** (`habitat_train_500`, not `habitat_0.8b_train_500`).
This is deliberate: `compare_evals.py:train_size()` parses tags by prefix and
`load_runs()` finds the baseline via `tag.endswith("base")`. Keeping tags identical
means that logic needs no rework, and the two trees are structurally identical, which
is what makes the overlay in §4 trivial.

Existing idempotent-resume behaviour is retained: a stage whose `adapter/` or
`metrics.json` already exists is skipped, so a job that hits the time limit can just be
resubmitted.

### 3. LoRA target guard

`train.py` raises after `get_peft_model` if any configured target name matched zero
modules, listing the unmatched names.

The preflight above shows the 0.8B needs no target change, so this guard is not
required for *this* run — it exists because a silently-unmatched target produces an
adapter that trains less than intended (or nothing) and only reveals itself as a flat
loss curve hours into a GPU job. It is a permanent guard for every future model swap.

### 4. Cross-model comparison — `compare_evals.py --compare-dir`

```
uv run scripts/compare_evals.py \
    --eval-dir outputs/eval_habitat_0.8b --label 0.8B \
    --compare-dir outputs/eval_habitat --compare-label 2B \
    --meta data/prepared_habitat/meta.json
```

- **Table:** gains a model column; the two trees' rows are grouped by model.
- **Plot:** both models on the same axes. Colour encodes the metric (existing `SERIES`
  slots, unchanged); line style encodes the model — solid = primary, dashed =
  comparison. Base-model hlines drawn for both, annotated with their label.
- **Writes into the primary `--eval-dir` only.** The comparison tree is opened
  read-only, so re-running the comparison can never modify the 2B results.

`--compare-dir` is optional; omitting it produces exactly today's single-model output.

### 5. Incidental fixes

Both are one-line, model-labelling bugs directly in the path of this work:

- `TASK_TITLES` hardcodes "Qwen3.5-2B" in both entries — becomes driven by `--label`,
  otherwise every 0.8B plot would be captioned as 2B.
- The habitat path sweep calls `compare_evals.py` with no `--task`, so it defaults to
  `trajectory` and renders under the ShareRobot title. Caption corrected.

## Testing

CPU-only, via pytest (per the project's no-CPU-smoke-train constraint):

- LoRA target guard fires on a bogus target name and passes on the real list.
- `--compare-dir` loads and merges two fixture eval trees; asserts the comparison tree
  is not written to.
- `--model-id` defaults to the 2B in both `train.py` and `evaluate.py` (argparse-level
  check — guards the "existing commands are unchanged" promise).

The sbatch model-arg mapping is verified by inspection rather than pytest: testing it
would mean either executing the scripts (which reach for the GPU) or adding a
dry-run mode that exists only for the test. The mapping is a three-line `case`
statement whose failure mode — a typo'd arg — is already covered by making an
unrecognised argument exit non-zero.

## Execution order

1. Code changes + tests green on the login node.
2. `sbatch slurm/run_all_habitat.sbatch 0.8b`
3. `sbatch slurm/run_all_habitat_choice.sbatch 0.8b`
4. `compare_evals.py --compare-dir` for each task once both sweeps finish.

Each sweep is 4 training runs + 5 evals. The 2B equivalents ran ~2–3 h on a 3g.40gb
slice; 0.8B should be faster, and the 24 h limit is retained unchanged.

## Out of scope

- Any hyperparameter tuning for 0.8B (see Goal — this is a fixed-budget A/B).
- Re-running the 2B sweeps.
- The ShareRobot phase-1 experiment.
- HTML report model-toggle (`visualize_choice_results.py` / habitat report). Worth
  revisiting once the numbers are in; not built speculatively.
